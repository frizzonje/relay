# Протокол relay (спецификация для клиентов)

Языконезависимое описание протокола сервер↔клиент. Источник правды по типам —
[`packages/shared/src/index.ts`](../packages/shared/src/index.ts) (TypeScript);
этот документ — его перевод для нативных клиентов (Swift, Kotlin, …), которые
не могут импортировать TS-пакет. **При изменении контракта обновлять оба файла.**

Все клиенты (web, iOS, desktop) — равноправные потребители одного API.
Сервер ничего не знает о платформе клиента.

## 1. Транспорты

Всё ходит через один origin (Caddy, TLS):

| Канал | Путь | Назначение |
|---|---|---|
| REST | `/api/*` | логин, ICE-конфиг, загрузка файлов |
| Socket.io v4 | `/socket.io` | сигналинг WebRTC, чат, реестры, presence |
| Статика | `/uploads/*` | отдача загруженных вложений |
| WebRTC | P2P (mesh) | медиа: аудио/видео/экран, напрямую между клиентами |

Socket.io — не «чистый» WebSocket: нужен socket.io-клиент
(iOS — `socket.io-client-swift`, Android — `socket.io-client-java`, поддерживать
версию протокола Engine.IO 4 / Socket.IO 4).

## 2. Аутентификация

Один общий пароль на инсталляцию (`SITE_PASSWORD`). Пустой пароль на сервере =
авторизация выключена, все запросы проходят без куки.

### 2.1 Логин

```
POST /api/login
Content-Type: application/json
{ "password": "..." }
```

- `200 {"ok":true}` + заголовок `Set-Cookie: relay_pass=<token>; HttpOnly; SameSite=Lax; Secure; Max-Age=2592000; Path=/`
  (web-фронт получает 201 от Nest — проверять `2xx`, не точный код);
- `401 {"error":"invalid password"}` — неверный пароль;
- `429 {"error":"too many attempts"}` — rate-limit: 8 неудач с одного IP за 10 минут.

### 2.2 Токен

`<exp>.<sig>`, где `exp` — миллисекунды Unix-времени истечения (now + 30 дней),
`sig` — `base64url(HMAC-SHA256(key, строка exp))` без паддинга,
`key = "relay-auth-v1:" + SITE_PASSWORD`. Смена пароля на сервере мгновенно
инвалидирует все выданные токены. Клиенту токен непрозрачен — разбирать его
не нужно, только хранить и предъявлять.

### 2.3 Предъявление

Сервер принимает токен из трёх источников; проверяются **в этом порядке**
(первый непустой выигрывает):

1. **`auth`-поле socket.io-handshake** — `{ token }` (только для сокета);
2. **`Authorization: Bearer <token>`** — REST, `/uploads/*` и socket.io-handshake;
3. **кука `relay_pass`** — REST, `/uploads/*` и socket.io-handshake.

Web-фронт и Tauri (грузит web-UI) полагаются на куку — браузер шлёт её сам.
Нативным клиентам удобнее заголовок/`auth`-поле, чем эмулировать cookie-jar:

- REST и `/uploads/*` — `Authorization: Bearer <token>` (либо `Cookie`, если
  URLSession/OkHttp ведут cookie-jar сами);
- Socket.io handshake — `auth`-поле (предпочтительно) или заголовок. Примеры:
  - `socket.io-client` (JS/Tauri-обёртки) — `auth`-поле:
    `io(url, { auth: { token } })`;
  - `socket.io-client-swift` — заголовок (его `connectParams` уходят в query,
    а не в `auth`):
    `SocketManager(socketURL: url, config: [.extraHeaders(["Authorization": "Bearer \(token)"])])`.
  - Невалидный/отсутствующий токен → сервер молча делает `disconnect` сразу
    после подключения.

## 3. REST

### GET /api/config

ICE-серверы для RTCPeerConnection. Запрашивать перед первым звонком; ответ можно
кэшировать на сессию.

```json
{ "iceServers": [ { "urls": ["stun:..."], "username": "...", "credential": "..." } ] }
```

`username`/`credential` присутствуют только у TURN.

### GET /api/metrics

Нагрузка на железо, где стоит инсталляция, — то, что главный экран показывает
вместо заставки. Цифры **хоста**, а не контейнера: `/proc` в docker общий с
хостом, а диск меряется по тому с данными relay (загрузки + реестр). Опрашивать
не чаще раза в 2 с — таков такт выборки на сервере; чаще смысла нет, ответ
придёт из секундного кэша.

```json
{ "cpu": { "cores": 8, "usage": 0.27, "load1": 0.58 },
  "mem": { "total": 4108828672, "used": 1244651520 },
  "disk": { "total": 62747442151424, "used": 48340977844224 },
  "uptimeSec": 12530 }
```

`usage` — доля 0..1 за окно замера; `null`, пока первая выборка не готова.
`load1` — средняя за минуту, `null` вне Linux. `disk` целиком `null`, если
файловую систему не опросить. Байты — везде байты. `null` рисовать прочерком,
а не нулём: «не померили» и «ноль» — разные утверждения.

### POST /api/upload

`multipart/form-data`, поле `file`, максимум **25 МБ** (иначе 4xx).

```json
{ "id": "…", "url": "/uploads/ab12….png", "name": "исходное-имя.png",
  "size": 12345, "mime": "image/png", "kind": "image" }
```

`kind`: `image` | `audio` | `file` — подсказка для рендера.
`id` — одноразовый талон: отправить в `chat-message { uploadId }`, чтобы
прикрепить файл к сообщению. `url` — относительный, отдаётся `/uploads/*`
(нужна та же кука).

## 4. Socket.io: подключение

- Немедленно после успешного handshake сервер шлёт четыре события:
  `settings`, `servers`, `channels`, `voice-presence` (полные снапшоты). Тому,
  кто предъявил личность, следом уезжает пятое — `presence` (§4.1).
- `settings` — действующие настройки инсталляции: снимок целиком, на
  подключении и при каждом изменении, всем сокетам одинаково (гостю по ссылке
  тоже). В него попадает только то, чем клиент пользуется — вид инсталляции,
  умолчания звука, битрейты, пределы, по которым он режет ввод; секретов в нём
  нет вовсе. Полную картину настроек видит панель владельца (§9), и это другое
  событие. Поля нет у сервера прошлой версии — тогда клиент живёт на
  умолчаниях, то есть как раньше.
- Включён connection-state-recovery: при коротком обрыве сессия
  восстанавливается с тем же `socket.id`; сервер даёт **24 с грейса** до
  оповещения остальных об уходе из комнат. Клиенту при `reconnect` со сменой id
  нужно заново `join`/`chat-join` (web-клиент так и делает).
- `socket.id` — идентификатор участника везде в протоколе (peer id).
- В `auth`-поле handshake рядом с токеном кладётся `clientId` — стабильный id
  устройства, который клиент хранит у себя (web — в localStorage). Он не
  пропуск и никого не удостоверяет; сервер по нему решает, чьи записи реестра
  человек вправе менять (§5), и выгоняет из голосового «призрака» — прошлый
  сокет того же устройства, ещё висящий в комнате после перезагрузки. Клиент,
  который его не шлёт, работает как прежде: его записи остаются без владельца.
  Объявлять себя надо именно здесь: в сообщениях этого поля больше нет.

### 4.1 Присутствие личности

Глобальная картина «кто сейчас на связи» — на всю инсталляцию, а не по
комнатам. `voice-presence` (§8.3) отвечает на другой вопрос — «кто в этой
комнате», — и для дозвона он не годится: звонят человеку, а не комнате.

| Направление | Событие | Payload | Примечание |
|---|---|---|---|
| S→C | `presence` | `PresenceEntry[]` | снимок на подключении |
| S→C | `presence-update` | `PresenceEntry[]` | только изменившиеся записи |

**PresenceEntry** `{ fingerprint, state, since }`, где `state` —
`online` (открыт хотя бы один клиент), `in-voice` (сидит в голосовом канале —
хоть с одного из своих устройств), `recent` (ушёл меньше двух минут назад) или
`offline`. `since` — мс Unix, когда это состояние началось.

Запись принадлежит **личности**, а не сокету: у человека с телефоном и
ноутбуком она одна, и `in-voice` с одного устройства сильнее `online` с
остальных. Адресуется она отпечатком ключа — тем же, которым адресуются ЛС (§7).

`offline` в снимке не встречается: нет записи — нет и человека. Приходит он
только дельтой, когда истекли две минуты `recent`. Дельта коалесцируется окном
80 мс, поэтому в одном событии приезжает пачка изменений.

Гость по инвайту в присутствии не участвует ни одной стороной: ни `presence`,
ни `presence-update` ему не приходят, и в чужой картине его нет — личности он
не предъявлял. То же и с клиентом, который ещё не стал личностью.

### 4.2 Дозвон

Звонок **человеку**, а не вход в комнату. Вызов живёт между двумя личностями до
ответа: он не принадлежит ни сокету (тот рвётся), ни голосовой комнате (её ещё
нет), поэтому переживает закрытую вкладку, пока у человека жив хоть один
клиент. Принятый вызов сажает двоих в голосовую комнату беседы — с этого
момента им владеет комната (§8), а не вызов.

| Направление | Событие | Payload | Примечание |
|---|---|---|---|
| C→S | `call-start` | `{ fingerprint, video? }` → ack | позвонить тому, чей это отпечаток |
| C→S | `call-accept` | `{ ringId }` → ack | принять — только тот, кому звонят |
| C→S | `call-decline` | `{ ringId }` → ack | отклонить — тоже только он |
| C→S | `call-cancel` | `{ ringId }` → ack | отбой — только звонящий |
| S→C | `call-incoming` | `{ ringId, from, at, video }` | на **все** устройства собеседника |
| S→C | `call-state` | `{ ringId, state, peer, at, video, room? }` | вызов жив: `ringing` или `accepted` |
| S→C | `call-ended` | `{ ringId, state, peer, at, missed }` | вызов кончился, не став разговором |
| S→C | `call-over` | `{ room }` | разговор кончился: собеседник ушёл |

`call-start` ack: `{ ok: true, ringId }` либо `{ ok: false, error }`, где `error` —
`disabled` (дозвон выключен в инсталляции), `forbidden` (правило `calls.whoCanCall`,
свой собственный отпечаток, гость по инвайту или клиент без личности), `offline`
(у собеседника нет ни одного живого устройства), `busy` или `rate` (исчерпан
`calls.maxRingsPerHour`).

`busy` значит две вещи сразу — собеседник уже в вызове либо говорит в голосовом
канале (`calls.busyWhenInVoice`). Различать их клиенту незачем: ответ один и тот
же, а рассказывать звонящему, где именно занят собеседник, значит рассказывать о
том больше, чем он показал сам.

`offline` — это отказ **до** вызова: набирать оказалось некуда. Исход `failed`
ниже — другое: собеседник пропал, когда у него уже звонило.

Ack трёх кнопок — `{ ok: true }` либо `{ ok: false, error: 'unknown' }`. `unknown`
означает «такого живого вызова нет» и покрывает заодно чужой `ringId` и чужую
кнопку: подтверждать постороннему, что вызов с таким id существует, сервер не
должен. Это не ошибка клиента, а проигранная гонка — успели отменить, вышел
таймаут, ответили с другого устройства.

**Участник** (`from`, `peer`) — `{ fingerprint, nick }`. Id личности в протоколе
не появляется, как и везде (§9.3). `peer` — это **вторая сторона глазами
получателя**: одно и то же событие уезжает двоим с разным содержимым этого поля.

**Состояния.** `ringing` → один из шести исходов: `accepted`, `declined`,
`no-answer`, `busy`, `cancelled`, `failed`. Разными они сделаны намеренно —
человеку на экране «отклонили», «не ответили», «занято» и «не в сети» объясняют
совершенно разные вещи. `failed` — собеседник исчез, не ответив; `cancelled` —
звонящий дал отбой сам.

**Исход `busy` сегодня не приходит никогда, и рисовать его клиенту не нужно.**
Занятость выясняется ДО того, как вызов заведён, и отвечается отказом `busy` в
ack `call-start` — то есть у звонящего нет вызова, которому было бы чем
кончиться, а у собеседника не звонило вовсе. Состояние оставлено и в машине, и в
типе `call-ended` на случай, когда «занят» начнёт присылать сам клиент
(например, отвечая на второй входящий во время разговора); до тех пор ветка под
него была бы мёртвой.

Каждый вызов кончается ровно одним из двух: `call-state` с `accepted` либо
`call-ended`. Третьего нет, и гадать, ждать ли ещё событие, клиенту не
приходится.

**Рассылка `call-state` асимметрична, и это не недосмотр.** `ringing` уходит
только звонящему — зато на все его устройства, чтобы набранный с ноутбука вызов
был виден и в телефоне. Собеседнику его слать нечего: тот же самый факт уже
приехал к нему `call-incoming`, причём в более полном виде (там ещё и кто
звонит), и второе событие о том же заставило бы клиента обрабатывать один факт
дважды и гадать, какое из двух пришло первым. `accepted`, наоборот, уходит
**обеим** сторонам: для звонящего это ответ, которого он ждал, для собеседника —
сигнал погасить входящий на тех его устройствах, где трубку не брали. Ни один из
двоих не может вывести это событие из того, что у него уже есть.

`missed` в `call-ended` — оставит ли этот исход отметку в переписке. Истинен для
`no-answer` и `failed` при включённом `calls.missedMarkEnabled`: это ровно те два
случая, о которых собеседник иначе не узнаёт вовсе. «Отклонён» он нажал сам,
«занято» случилось у него в разговоре, «отбой» — звонящий передумал.

**Правила дома** приезжают из каталога настроек (§9.1, группа `calls`) и
читаются в момент набора: `calls.enabled`, `calls.whoCanCall`
(`everyone` / `conversation` — с кем **заведена** переписка (§7) / `nobody`),
`calls.ringTimeoutSeconds`, `calls.videoAllowed` (выключенное превращает
видеозвонок в голосовой, а не отказывает), `calls.busyWhenInVoice`,
`calls.maxRingsPerHour` (считаются только состоявшиеся вызовы; принимать входящие
предел не мешает никогда), `calls.missedMarkEnabled`.

Вызов принадлежит **личности**: звонок доходит до всех её устройств, ответ с
одного гасит входящий на остальных, а обрыв одного сокета не значит ничего, пока
остался хоть один. Ушло последнее — вызов заканчивается сразу, без грейса:
`cancelled` со стороны звонящего, `failed` со стороны собеседника. Грейса нет
намеренно — оба конца смотрят на экран прямо сейчас, а любой осмысленный грейс
сравним со всем дозвоном целиком.

Личность участвует **не более чем в одном живом вызове**, с любой стороны. Из
этого правила выпадает и встречный звонок: двое, набравшие друг друга в одну
секунду, не остаются в двух вызовах — второй набор получает `busy`, а набравший
вторым видит входящий от первого и может его принять.

Гость по инвайту в дозвоне не участвует ни одной стороной: личности он не
предъявлял, адресовать его нечем.

**Комната беседы.** `room` есть только у `accepted` и называется
`voice:<адрес беседы>` — тот же адрес, что у переписки этих двоих (§7), с
приставкой. Приставка обязательна: комнаты socket.io у ленты и у эфира общие, и
без неё сигналинг звонка уезжал бы каждому, кто просто открыл переписку.
Вывести адрес клиент не может (он считается из id двух личностей, а id в
протоколе нет), поэтому сервер называет его сам — и обоим.

**Садится в комнату клиент, а не сервер.** Получив `accepted`, обе стороны
входят в неё обычным `join` (§8.1) — сервер за них этого не делает намеренно:
сесть в голосовую комнату значит взять микрофон и поднять транспорты, а
вписанный сервером сокет оказался бы в комнате молча — для собеседника есть, а
звука от него нет. Входит РОВНО ТО устройство, которое звонило или ответило:
`accepted` приезжает на все устройства обоих (оно же гасит входящий там, где
трубку не брали), и сядь по нему каждая вкладка, человека было бы слышно дважды.

У комнаты беседы три правила, и все три держит сервер, а не вежливость клиента:

- **Войти могут только двое, названные её адресом.** Постороннему — отказ
  `voice-refused` с причиной `not-in-call` (§8.1); ту же причину получает всякий,
  кто назвал комнату беседы, которой не открывали или которая уже кончилась.
  Разбирать эти два случая по-разному сервер не станет: иначе посторонний
  узнавал бы, что беседа с таким адресом существует.
- **Уход любого кончает разговор.** Второго сервер выводит из комнаты сам и
  говорит ему об этом событием `call-over`: комната на одного — это не звонок на
  удержании. Грейс тот же, что у голосового канала (24 с): моргание сети
  разговор не рвёт, а `call-over` доезжает и до того, у кого она моргнула.
- **Не сел второй за полминуты — комната кончается сама.** Войти может не
  выйти: в движке нет WebRTC, человек не дал микрофон, вкладку закрыли сразу
  после «принять». Сервер узнаёт об этом только по тому, что второй не пришёл, —
  и закрывает комнату тем же `call-over`, вместо того чтобы оставить первого
  слушать тишину. Считаются именно вошедшие, а не живые сокеты: обрыв связи
  посреди разговора этого срока не касается, его переживают окно восстановления
  и грейс.

Отсюда клиентское правило: **`voice-refused` с причиной `not-in-call` обязан
кончить звонок у себя** — отпустить микрофон и снять экран, — а не показать
сообщение. Такой отказ доходит и до законного участника: пока у него висел
системный запрос доступа к микрофону, комнату успел закрыть тот самый сторож.
В комнату он при этом не вошёл, а значит `call-over` до него не доедет никогда.
- **Медиасервера у неё не бывает.** Двоим он не нужен никогда: `sfu-token` на
  комнату беседы отвечает `not-sfu`, а транспорт, названный клиентом в `join`,
  для неё не спрашивается вовсе — всегда `p2p`.

Другое устройство того же человека, войдя в комнату беседы, разговор не
утраивает: он переезжает к нему, а прежнее устройство получает `call-over`.

**Честное ограничение:** входящий доходит, только если у человека открыт клиент.
Пушей у relay нет, и мобильный веб в фоне вызова не поймает. Интерфейс обязан
говорить об этом на экране исходящего, а не только в этом документе.

## 5. Реестры серверов и каналов

Реестр общий на инсталляцию, персистится на сервере. Снапшоты приходят целиком
при каждом изменении — клиент просто замещает своё состояние.

**Server** `{ id, name, emoji?, removable, locked?, mine? }` — «гильдия».
**Channel** `{ id, serverId, type: "text"|"voice", name, slug, removable, mode?, lastTs?, mine? }` —
`slug` уникален глобально и служит именем socket.io-комнаты; `mode` (`"sfu"`,
иначе p2p) есть только у голосовых, `lastTs` — время последнего сообщения в
текстовом.

**Владение.** `mine: true` — «этой записью управляешь ты»: её создало это
устройство (`clientId` из handshake) либо у неё нет владельца вовсе (создана до
правила). Ровно по этому условию сервер пускает переименование, удаление, смену
режима и запросы среза, поэтому кнопки рисуют по нему — иначе действие получит
отказ. Сам `clientId` владельца наружу не уходит: флаг считается на сервере под
каждый сокет отдельно. Это заслон от случайного сноса, а не права доступа —
`clientId` подделывается тем, кто его знает.

| Направление | Событие | Payload | Примечание |
|---|---|---|---|
| S→C | `servers` | `Server[]` | без хэшей паролей, только флаг `locked` |
| S→C | `channels` | `Channel[]` | каналы закрытых серверов скрыты до unlock |
| C→S | `server-create` | `{ id, name, emoji?, password? }` | `id` генерирует клиент (UUID) |
| C→S | `server-delete` | `{ id }` → ack | главный сервер неудаляем |
| C→S | `server-stats` | `{ id }` → ack | цена удаления: `{ channels, messages, occupants }` |
| C→S | `server-unlock` | `{ id, password }` | доступ к закрытому серверу |
| S→C | `server-unlock-result` | `{ id, ok }` | при `ok` следом приходит `channels` |
| C→S | `channel-create` | `{ serverId, type, name, mode? }` | сервер сам делает id/slug; лимит 50 каналов |
| C→S | `channel-delete` | `{ id }` → ack | |
| C→S | `channel-rename` | `{ id, name }` → ack | |
| C→S | `channel-stats` | `{ id }` → ack | `{ occupants, messages }` |
| C→S | `channel-mode` | `{ id, mode }` | только голосовые; ответа нет |

Ack — `{ ok: true }` либо `{ ok: false, error }`: `not-found`, `bad-name`
(пустое имя в `channel-rename`), `forbidden` (закрытый сервер не разблокирован,
либо запись неудаляемая), `not-owner` (создано другим устройством), `occupied`
с полем `occupants` — в голосовом
канале кто-то есть, и разговор дороже уборки; удаление сервера отказывает по
той же причине, если люди сидят в любом из его каналов. Срез (`*-stats`)
отдаётся только владельцу: сколько в канале людей и сообщений — уже данные о
нём.

## 6. Текстовые каналы

| Направление | Событие | Payload |
|---|---|---|
| C→S | `chat-join` | `{ room: slug, name? }` |
| C→S | `chat-leave` | — |
| C→S | `chat-message` | `{ text? }` или `{ uploadId? }` (талон из /api/upload) |
| C→S | `chat-react` | `{ id: messageId, emoji }` — повторная отправка снимает реакцию |
| S→C | `chat-history` | `ChatMessage[]` — последние ≤50, сразу после join |
| S→C | `chat` | `ChatMessage` — новое сообщение (включая системные вход/выход) |
| S→C | `chat-roster` | `string[]` — имена присутствующих в канале |
| S→C | `chat-reaction` | `{ id, reactions: { emoji: name[] } }` |
| S→C | `chat-closed` | `{ slug }` — канал удалён: сервер выписал тебя из комнаты, закрой ленту |

`chat-join` в несуществующий текстовый канал не пускает: в ответ прилетит
`chat-closed`, комнаты не будет (а значит, и `chat-message` уйдёт в никуда).
Каналы закрытого сервера доступны только после `server-unlock` — до него
`chat-join` молча ничего не делает.

**ChatMessage** `{ id?, name?, text, ts, attachment?, system?, reactions? }` —
`ts` в мс Unix; `system: true` — сервисное сообщение, рисовать иначе.
Реакции валидируются по списку: `👍 👎 ❤️ 😂 🔥 🫡 🤡 😭`.
Лимиты: текст ≤500 символов, имя ≤20, slug ≤32 (сервер усечёт сам).

## 7. Личные сообщения

Беседа 1:1 — тот же канал, что и у групповых, но без сервера над ним и без
видимости в реестре: `channels` её никогда не перечисляет. Реплики в ней ходят
обычными `chat-*` событиями (`chat-join` вместо `dm-join` после входа,
`chat-message`, история, реакции, правка, удаление — без изменений); события
ниже только про адресацию и список переписок.

Гость по инвайту в ЛС не участвует ни одной стороной: ни списка переписок, ни
`dm-open` на него нет.

**Честная строка о приватности:** переписки читаемы владельцем инсталляции —
это данные на его сервере, а не сквозное шифрование. Интерфейс обязан говорить
об этом прямо, а не только этот документ.

| Направление | Событие | Payload | Примечание |
|---|---|---|---|
| C→S | `dm-open` | `{ fingerprint }` → ack | открыть (или найти) переписку с этим отпечатком |
| C→S | `dm-list` | → ack | мои переписки — спрашивается при входе в раздел |
| C→S | `dm-join` | `{ slug }` → ack | сесть в ленту беседы; отдельная дверь от `chat-join` — пускает по членству в паре, а не по видимости в реестре |
| C→S | `dm-people` | `{ query? }` → ack | кого инсталляция видела — список для выбора собеседника; пустой `query` — просто список |
| S→C | `dm-activity` | `{ slug, ts, preview, previewMine, peer }` | в беседе написали — только двоим участникам, а не всей инсталляции (в отличие от `chat-activity`) |

`dm-open` ack: `{ ok: true, conversation }`, где `conversation` — строка
раздела (`{ slug, peer: { fingerprint, nick }, lastTs, preview, previewMine }`);
либо `{ ok: false, error }` с `unknown` (такой личности инсталляция не знает),
`self` (нельзя открыть переписку с собой) или `forbidden` (ЛС не для тебя).

`dm-join` ack: `{ ok: true }` либо `{ ok: false, error }` — `unknown` или
`forbidden`.

`dm-list` ack: `{ ok: true, conversations: DmConversation[] }` либо
`{ ok: false, error: 'forbidden' }`.

`dm-people` ack: `{ ok: true, people }`, где `people` — `{ fingerprint, nick,
lastSeenTs }[]` (`lastSeenTs: 0` — не видели ни разу), либо
`{ ok: false, error: 'forbidden' }`.

`preview` в списке переписок и в `dm-activity` обрезано до 120 символов —
второй запрос ради последней реплики был бы запросом на каждое сообщение.

## 8. Голос (mesh-WebRTC)

Топология — full mesh: каждый с каждым, отдельный RTCPeerConnection на пару.
Практический потолок ~6–7 участников (для большего — план SFU,
[plans/old/sfu.md](plans/old/sfu.md)).

### 8.1 Вход/выход и сигналинг

| Направление | Событие | Payload |
|---|---|---|
| C→S | `join` | `{ room: slug, name? }` — одна голосовая комната на сокет |
| C→S | `leave` | — |
| S→C | `peers` | `VoicePeer[]` — кто уже в комнате (ответ на join) |
| S→C | `peer-joined` | `{ id, name? }` |
| S→C | `peer-left` | `{ id }` |
| C→S | `offer` / `answer` | `{ to: peerId, sdp: { type, sdp } }` |
| S→C | `offer` / `answer` | `{ from: peerId, name?, sdp }` |
| C→S | `ice-candidate` | `{ to, candidate: { candidate, sdpMid, sdpMLineIndex, usernameFragment } }` |
| S→C | `ice-candidate` | `{ from, candidate }` |

Сервер только пересылает SDP/ICE адресату (`to` → `from`), не заглядывая внутрь.

`room` — слаг голосового канала либо адрес комнаты беседы (§4.2). Комната, за
которой нет канала реестра, обычно не заперта ничем (её мог удалить владелец под
живым разговором, или это комната приглашения) — кроме комнаты беседы: та
пускает только двоих, а всем остальным отвечает `voice-refused` с причиной
`not-in-call`.

### 8.2 Правила соединения (perfect negotiation)

1. **Новичок инициирует**: получив `peers`, шлёт offer каждому из списка.
   Существующие участники не делают ничего, пока не получат offer.
2. Роли glare-разрешения детерминированы: для пары (A, B)
   **polite тот, чей `socket.id` лексикографически меньше** id собеседника.
   Невежливая сторона при коллизии (одновременные offer) игнорирует входящий
   offer, вежливая — откатывается (`rollback`) и принимает.
3. ICE-кандидаты, пришедшие до `setRemoteDescription`, буферизуются и
   применяются после.
4. Реконнект медиа: при `connectionState == "disconnected"` дольше ~8 с —
   `restartIce()`; при `failed` — пересоздание соединения.

### 8.3 Состояние медиа и presence

| Направление | Событие | Payload |
|---|---|---|
| C→S | `media-update` | `{ camOn, screenOn, micOn?, deafened? }` — слать сразу после join и при каждом изменении |
| S→C | `media-update` | то же + `from: peerId` |
| C→S | `rename` | `{ name }` — смена имени на лету |
| S→C | `peer-renamed` | `{ id, name }` |
| S→C | `voice-presence` | `{ [roomSlug]: VoicePeer[] }` — глобальная карта «кто где», рассылается всем при каждом изменении |

**VoicePeer** `{ id, name?, micOn?, deafened? }`; отсутствующий `micOn`
трактовать как «включён».

Медиа-треки: аудио всегда, видео/экран добавляются через
`replaceTrack`/renegotiation (см. `apps/web/lib/voice.ts` как референс-реализацию;
битрейт видео капится ~900 кбит/с).

## 9. Админ-панель

Панель инсталляции — восемь событий с ack, и **все только для владельца**.
Владение проверяет каждое событие само: клиент, не показавший кнопку, ничего не
запрещает, а событие в socket.io шлёт кто угодно. Любому, кто не владелец
(включая гостя по ссылке и клиента без личности), приходит
`{ ok: false, error: 'forbidden' }` — на каждое из восьми. Власть меняется под
живым сокетом: открывший новую ссылку владельца становится им сразу, прежний
теряет доступ к панели тем же мгновением, без переподключения.

Владелец у инсталляции ровно один, второй роли в панели нет. Модератор сервера —
власть над своим сервером (§6), панель меняет инсталляцию целиком.

| Направление | Событие | Payload | Примечание |
|---|---|---|---|
| C→S | `admin-state` | → ack | каталог параметров, значения и сводка одним ответом |
| C→S | `admin-set` | `{ key, value, confirm? }` → ack | записать один параметр |
| C→S | `admin-reset` | `{ group, confirm }` → ack | вернуть группу к умолчаниям каталога |
| C→S | `admin-people` | `{ query?, cursor? }` → ack | страница людей: лицо, имя, устройства, положение |
| C→S | `admin-bans` | → ack | забаненные на всю инсталляцию |
| C→S | `admin-audit` | `{ cursor? }` → ack | страница журнала, от свежих к старым |
| C→S | `admin-action` | `{ action, target?, confirm?, values? }` → ack | то, что делают кнопкой, а не полем |
| C→S | `admin-password` | `{ password, confirm }` → ack | сменить пароль инсталляции |
| S→C | `admin-changed` | `{ keys, values }` | параметр поменяли из ДРУГОЙ сессии владельца |

### 9.1 Каталог и значения

`admin-state` ack: `{ ok: true, catalog, values, overview }`.

`catalog` — список параметров с сервера: `{ key, group, kind, fallback,
applies, min?, max?, options?, secret?, danger?, env?, readOnly?, client? }`.
Панель рисует поля **по нему**, а не по своей копии: параметры добавляются в
любом выпуске, а версия контракта поднимается только с мажором.

`values` — действующие значения по тем же ключам. **Значения секретов не
уезжают никогда**: у параметра с `secret: true` вместо строки приходит `true` /
`false` — «задано» или «нет». Это свойство каталога, а не дисциплина экрана.

`overview` — сводка: `{ people, online, bans, messages, servers, channels,
storageBytes, storageQuotaBytes, retention, directRetention, version }`.
`retention` — `{ mode: 'days' | 'forever' | 'ephemeral', days? }`;
`directRetention` — то же для личной переписки либо `null`, если её срок общий с
каналами.

### 9.2 Запись

`admin-set` ack: `{ ok: true, key, changed, value }` — `changed: false` значит
«уже было таким», и это не отказ. Иначе `{ ok: false, error }`, где `error`:

| Причина | Что случилось |
|---|---|
| `forbidden` | не владелец (а у `revoke-device` — ещё и «это твоё текущее устройство») |
| `needs-confirm` | опасное (`danger` в каталоге) прислали без `confirm: true` |
| `unknown-key` | такого параметра (или группы) в каталоге нет |
| `read-only` | параметр живёт в окружении, панель его только показывает |
| `wrong-type`, `out-of-range`, `not-an-option`, `too-long` | значение не проходит проверку каталога |
| `secret-path` | у секрета своя дорога, общей записью он не меняется |
| `not-found` | цели действия нет: такого отпечатка, устройства или бана |
| `unsupported` | сервер не знает такого действия — клиент новее сервера |

**Подтверждение — поле в запросе, а не диалог на экране.** Параметр с
`danger: true` без `confirm: true` не записывается; `admin-reset` требует
подтверждения всегда — это правка десятка полей одним нажатием.

`admin-reset` ack: `{ ok: true, group, changed, values }` — `changed` перечисляет
ключи, у которых значение действительно стало другим.

Секретов запись не принимает вовсе: у пароля инсталляции своя дорога (§9.5), и
`admin-set` на нём отвечает `secret-path`, а не «сохранено».

### 9.3 Люди, баны, журнал

`admin-people` ack: `{ ok: true, people, cursor? }`, где человек —
`{ fingerprint, nick, createdAt, lastSeenAt, devices, banned, owner }`, а
устройство — `{ id, name, lastSeenAt, revoked }`. Лицо рисуется из
отпечатка ключа, id личности в протоколе не появляется вовсе. `query` ищет и по
нику, и по отпечатку; `cursor` есть в ответе, только если ниже что-то осталось.
Негодный курсор — пустая страница, а не первая.

`admin-bans` ack: `{ ok: true, bans }` — `{ fingerprint, nick, at, by }[]`,
только баны на всю инсталляцию.

`admin-audit` ack: `{ ok: true, entries, more }`. Курсор страницы полный
(`{ at, id }`): в одну миллисекунду попадает несколько записей. Строка журнала —
`{ id, at, actor?, actorNick, system?, action, target?, detail }`; `actor` —
отпечаток действовавшего, `system: true` — действовала машина, и узнавать её
надо по этому полю, а не по тексту ника.

### 9.4 Действия

`admin-action` ack: `{ ok: true, action, link?, settings?, imported?, count? }`.
Подтверждения (`confirm: true`) просят все действия, кроме выгрузки.

| Действие | Что делает | Что в ответе |
|---|---|---|
| `owner-link` | перевыпускает ссылку владельца; прежняя умирает | `link: { token, expiresAt }` — **ключ уезжает один раз и больше нигде** |
| `retention-run` | прогоняет ретенцию сейчас | `count` — сколько реплик удалено |
| `files-sweep` | подметает осиротевшие вложения | `count` — сколько унесено |
| `revoke-sessions` | обесценивает все выданные сессии | `count` — сколько сокетов оборвано |
| `revoke-device` | отзывает устройство (`target` — его id) | `count` — сколько сокетов оборвано |
| `ban` / `unban` | бан на всю инсталляцию (`target` — отпечаток) | — |
| `export` | выгружает настройки | `settings: { protocol, at, values }` |
| `import` | применяет настройки из `values` | `imported: { applied, rejected }` |

Выгрузка не содержит ни секретов (даже признаком «задано»), ни
инфраструктурного (`readOnly`) — оно живёт в `.env` конкретной машины. Импорт
применяет годное и **перечисляет отвергнутое** с причиной из той же таблицы
отказов: `rejected: { key, reason }[]`. В `applied` попадает только то, что
действительно изменилось.

`revoke-sessions` задевает и того, кто нажал: его кука умирает вместе с чужими,
и клиент проходит челлендж личности заново — ключ у него на руках, и человека
об этом не спрашивают. Сокет нажавшего при этом не рвётся: иначе ответ было бы
некому доставить. Своё текущее устройство
`revoke-device` не отзывает: ключ этого устройства — единственный способ
вернуться.

### 9.5 Пароль инсталляции

`admin-password` `{ password, confirm: true }` → ack
`{ ok: true, set, changed, count }`.

У пароля **своя дорога**: он единственный параметр, который одновременно
секрет, хранится хэшем (scrypt) и отзывает всё выданное. `admin-set` на нём
отвечает `secret-path` — не «пока не поддерживается», а «не этой дверью».

`password: ''` снимает пароль, заданный из панели. Инсталляция при этом не
обязательно открывается: под ним может лежать `SITE_PASSWORD` из окружения, и
она возвращается к нему — панель главнее переменной, переменная остаётся
резервом.

`set` — заперта ли инсталляция теперь; `changed: false` — ничего не поменялось
(снимали пароль там, где его и не было); `count` — сколько живых сокетов
оборвано. Значение пароля обратно не уезжает ни в каком виде: сервер знает
только хэш. В журнал попадает `password-changed` — факт и `{ set }`, без
значения и без его длины.

Смена отзывает **всё выданное сразу**: пропуска `relay_pass` и гостевые ссылки
подписаны паролем и умирают сами, сессии личностей отзываются вслух (как
`revoke-sessions`), живые сокеты рвутся все, кроме сокета нажавшего. Старый
пароль перестаёт пускать в тот же миг, перезапуск не нужен.

**Ворота включены, а пароля нет — это отсутствие ворот.**
`access.sitePasswordEnabled` включён по умолчанию, но инсталляция без пароля
пускает всех, как и до панели; флажок дверь выключает, а не заводит.

### 9.6 Правка из другой сессии

`admin-changed` `{ keys, values }` летит **только сокетам владельца и только
другим, не тому, кто правил**: панель, открытая на втором устройстве, обязана
обновиться, иначе она сохранит поверх свежей правки вчерашнее. Это не замена
общему событию `settings` (§4): в общий снимок попадает лишь помеченное в
каталоге `client`, а панели нужно всё, что она показывает.

## 10. Устаревшее — в новых клиентах не реализовывать

- событие `track` и связанное поле `oko` в `ChatMessage` — legacy из ранней
  версии протокола, полностью удалены;
- localStorage-ключ web-клиента `relay-tag` — деталь web-реализации, не часть
  протокола.

## 11. Чек-лист нового клиента

1. `POST /api/login` → взять токен из `Set-Cookie: relay_pass=…` и сохранить
   (Keychain/защищённое хранилище).
2. Socket.io-подключение с токеном в `auth`-поле (или `Authorization`-заголовке,
   §2.3) → принять `servers`/`channels`/`voice-presence`/`presence`.
3. Чат: `chat-join` → история/roster → `chat-message`/`chat-react`.
4. Звонок: `GET /api/config` → `join` → offer'ы всем из `peers` по правилам 8.2
   → `media-update` → рендер треков.
5. Обработать: `disconnect` сразу после connect (= кука протухла → релогин),
   `server-unlock-result`, реконнект с повторным `join`.
