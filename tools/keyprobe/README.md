# Проба ключа личности

Этап 0 плана [1.0](../../docs/plans/relay-1.0.md) спрашивает одно: переживает ли
перезапуск приложения приватный ключ, который **нельзя достать из движка**
(`extractable: false`), и работает ли это во всех трёх webview, а не только в
браузере. Слой 2 (личность на ключах) целиком стоит на положительном ответе.

Проверять это спецификацией бесполезно — спецификация разрешает. Нас в этих
webview уже кусали `getUserMedia` в WKWebView и профили H264 там же.

## Запуск

```bash
docker run --rm -p 4321:4321 -v "$PWD/tools/keyprobe":/probe:ro -w /probe node:20-alpine node serve.mjs
```

Дальше открыть в проверяемом движке — `http://localhost:4321/`. Вердикт виден
на странице **и** уходит в лог сервера: окно webview на чужой платформе может
быть некому показать.

- `/` — обычная проба: ключ, IndexedDB, подпись, запрет экспорта. Гонять
  **дважды**, с полным перезапуском приложения между заходами: первый запуск
  ключ создаёт, второй читает и говорит `survived a restart`.
- `/matrix.html` — что этот движок вообще хранит: обычный объект, извлекаемый
  ключ, неизвлекаемый ключ в объекте и он же голым значением. Каждый вариант в
  своём воркере, под сторожем; `?second` — не писать, только читать
  сохранённое.
- `?reset` — удалить базу перед прогоном, `?db=NAME` — своя база под опыт,
  `?nomarker` — только ключ, без обычной записи рядом.

Прогон в десктоп-оболочке, без ввода адреса руками (identifier чужой, чтобы
плагин single-instance не отдал запуск установленному клиенту):

```bash
cargo tauri dev --no-watch --config '{"identifier":"app.relay.desktop.keyspike","productName":"relay-keyspike","app":{"windows":[{"label":"main","url":"http://localhost:4321/matrix.html"}]}}'
```

## Почему проба устроена сложнее, чем задача

Три приёма здесь не от любви к искусству — без них WKWebView отвечает молчанием,
неотличимым от «страница не загрузилась»:

1. **Маячок на каждую стадию, с ожиданием доставки.** Зависшая операция
   IndexedDB в WebKit уносит с собой сетевой процесс (в WebKit это один и тот
   же процесс) — маячок, отправленный и не дождавшийся ответа, до сервера уже
   не доедет, и последняя стадия в логе окажется не той, на которой встало.
2. **Запрос из разметки** (`<img src="/log?...">`) до всякого JS — отделяет
   «страница не дошла» от «JS не выполнился».
3. **Воркеры в матрице.** Зависание блокирует поток вместе с `setTimeout`, так
   что сторож на самой странице не срабатывает. Воркер убивается снаружи.

## Результаты (2026-08-12)

| Движок | Итог |
|---|---|
| Chromium 148 (Electron) | всё проходит: Ed25519, неизвлекаемый ключ в IndexedDB, подпись после перезапуска, экспорт запрещён |
| Safari 26.5.2 (тот же AppleWebKit 605.1.15) | всё проходит, оба запуска: ключ пережил полный выход из браузера и подписал |
| WKWebView (macOS 15, AppleWebKit 605.1.15) | **CryptoKey в IndexedDB вешает движок** — подробности ниже |
| WebView2 (Windows) | не проверено, машины нет |
| WebKitGTK (Linux) | не проверено, машины нет |
| Firefox (Gecko) | не проверено, браузера на машине нет |

**Safari и WKWebView — один и тот же движок одной и той же версии, и ведут они
себя противоположно.** Значит дело не в WebKit и не в спецификации, а в том, чем
хост-приложение отличается от Safari. Главное отличие — подпись: Safari подписан
Apple с настоящим Team ID и правом на keychain, relay для macOS подписан ad-hoc.
Заодно это снимает вопрос с веб-клиента на маке: в браузере всё работает.

В WKWebView работает всё, кроме хранения: `Ed25519` есть, `generateKey` с
`extractable: false` проходит, подпись сходится, экспорт приватной половины
запрещён, обычный объект в IndexedDB кладётся и читается после перезапуска
приложения. Падает ровно `put` записи, содержащей `CryptoKey`: он не
завершается ни успехом, ни ошибкой, и вместе с ним встаёт весь процесс
хранилища — после этого страница не может ни в IndexedDB, ни в сеть. Извлекаемый
ключ ведёт себя так же, то есть дело не в `extractable`. Один раз запись прошла,
но следующий запуск завис уже на чтении; база после этого не открывается, пока
её не удалить (`?reset`).

Правдоподобная причина, **не доказанная**: WebKit хранит `CryptoKey` завёрнутым
в мастер-ключ из keychain приложения, а relay для macOS подписан ad-hoc и без
Team ID (это верно и для `/Applications/relay.app`, не только для dev-сборки) —
в момент первого прогона в системе поднялся `SecurityAgent`. Если причина эта,
она лечится настоящей подписью Developer ID, то есть счётом у Apple.
