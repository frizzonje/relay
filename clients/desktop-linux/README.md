# relay desktop для Linux — Electron

Нативный клиент relay под Linux: то же окно, тот же web-UI, но движок —
Chromium. Отдельная оболочка существует ровно по одной причине, и она не про
вкусы.

## Почему не Tauri, как на Windows и macOS

Tauri берёт **системный** webview, а на Linux это WebKitGTK, собранный **без
WebRTC**: upstream держит `-DENABLE_WEB_RTC=OFF` по умолчанию, и мейнстрим-
дистрибутивы флаг не включают. В таком движке `getUserMedia` на месте (микрофон
спросится и выдастся), а `RTCPeerConnection` попросту нет — клиент заходил в
голосовой канал, зажигал микрофон и молчал.

Проверено заново **21 августа 2026** на самых свежих стабильных сборках:

| Дистрибутив | WebKitGTK | Результат |
|---|---|---|
| Debian 13 (trixie) | 2.52.5 | `RTCPeerConnection` — `undefined` даже при `enable-webrtc=True`; `getUserMedia`/`getDisplayMedia` при этом на месте |
| Fedora 44 | 2.52.5 | в `libwebkit2gtk-4.1.so.0` нет строк `createOffer`, `addIceCandidate`, `setRemoteDescription` |
| Arch, Ubuntu 22.04 | 2.52.5 / 2.50.4 | то же самое (проверялось раньше, см. `clients/desktop/README.md`) |

Upstream движется — в 2.52 (март 2026) WebRTC-сеть GstWebRTC вынесли в
network process, — но по умолчанию флаг всё ещё выключен, и до дистрибутивов
это дойдёт не в этом году. Заменить движок у Tauri тоже нечем: CEF-бэкенд «не
снят со стола, ETA нет», Servo/Verso — эксперимент без WebRTC.

Поэтому под Linux — Chromium, то есть Electron. Проверено там же: Electron 43
(Chromium 150) в контейнере с Xvfb поднимает соединение и гонит по нему RTP.

## Что умеет и чего не умеет

| | Linux (Electron) | Windows / macOS (Tauri) |
|---|---|---|
| Звонки, видео, демонстрация экрана | ✅ | ✅ |
| Экран выбора сервера, «сменить сервер» | ✅ (общая страница) | ✅ |
| Ключ личности живёт вне webview | ✅ (файл `0600`) | ✅ (Keychain / Credential Manager) |
| Трей со статусом звонка, уведомления | ✅ | ✅ |
| Автозапуск при входе в систему | ✅ (`~/.config/autostart`) | ✅ |
| Автообновление | ✅ AppImage | ✅ |
| Глобальный PTT-хоткей | ❌ пока нет | ✅ |
| Системный звук демонстрации экрана | ❌ движок не отдаёт | ✅ Windows |

Два «нет» — честные, и вот почему:

- **Глобальный хоткей.** На X11 он завёлся бы сразу, но на Wayland глобальные
  хоткеи идут через портал `GlobalShortcuts`, у которого прямо сейчас открытые
  баги (регрессия в Electron 40.x; с `xdg-desktop-portal` ≥ 1.20 приложение
  обязано звать `Registry.Register`, чего Chromium не делает). Половинчатый
  хоткей «работает у одних, молчит у других» хуже отсутствующего, поэтому
  оболочка его не показывает вовсе: `desktop-settings` не содержит `pttDefault`,
  и web-UI не рисует строку с рекордером клавиш (см. `stores/desktop.ts`).
- **Звук демонстрации.** Портал Wayland отдаёт только видео, а loopback-захват
  Chromium умеет на Windows и macOS. Демонстрация идёт без системного звука —
  как в браузере на той же машине.

## Архитектура

Как и Tauri-клиент, это **site-specific browser**: окно грузит адрес
инсталляции, который человек ввёл на экране выбора сервера, а весь UI приезжает
с сервера. Фронт не форкается: задеплоил web — обновился и десктоп.

```
clients/desktop-linux/
  src/main.js                 жизненный цикл, окно, навигация, мост, трей
  src/preload.js              мост для страницы сервера (contextBridge, sandbox)
  src/events.js               СПИСОК разрешённых событий — граница доверия
  src/identity.js             ключ Ed25519 на origin: файл 0600
  src/settings.js             settings.json + автозапуск (~/.config/autostart)
  src/media.js                разрешения + выбор источника демонстрации
  src/screen-picker.html/.js  свой выбор источника (X11; на Wayland — портал)
  src/tray.js                 трей: статус звонка, en/ru
  src/updater.js              обновления AppImage (electron-updater)
  src/paths.js, log.js, url.js, assets.js
  testbench/                  стенд: живой звонок оболочки с браузером в Docker
```

Своей страницы у клиента одна — экран выбора сервера, и он **общий с
Tauri-клиентом**: `../desktop/src/index.html`. Копии нет намеренно, иначе две
оболочки разъедутся внешне; в сборку файлы попадают через `extraResources`.

### Мост

Только события, ровно те же имена, что у Tauri-клиента (см. `src/events.js`):

- оболочка → страница: `desktop-settings`, `update-status`, `identity-reply`;
- страница → оболочка: `voice-status`, `desktop-settings-get`, `set-autostart`,
  `switch-server`, `check-updates`, `install-update`, `identity-request`,
  `screen-picker`, `webrtc-missing`.

Со стороны web это один и тот же код — `apps/web/lib/shell-bridge.ts` находит
мост в `window.__TAURI__.event` или в `window.__RELAY_SHELL__`, а всё остальное
(`lib/desktop.ts`, `lib/signer-shell.ts`) разницы не видит.

Страница грузится с чужого сервера, поэтому её права ограничены так же, как у
Tauri через `capabilities/remote.json`: `contextIsolation`, `sandbox`, никакого
Node, мост — две функции, и события не из списка отклоняются с внятной ошибкой
(её видно в консоли страницы, а не «оболочка просто ничего не умеет»).

### Ключ личности

Родится, живёт и подписывает в главном процессе; страница знает только свой
публичный ключ и умеет просить подпись. Формат и путь — **байт в байт как у
Tauri-клиента**: `~/.config/app.relay.desktop/identity/<8 байт sha256(origin)>.key`,
права `0600`, содержимое — base64url 32-байтового семени. Это не косметика:
человек, обновившийся с Tauri-сборки, остаётся собой — с тем же ключом, лентой
и именем. Ключ **свой у каждого origin**: оболочка умеет «сменить сервер», и
общий ключ означал бы, что сервер A может попросить подписать нонс сервера B.

Новый ключ рождается только когда хранилище внятно ответило «такого нет».
Отказ (каталог не читается, файл битый) — это отказ и экран беды, а не молча
заведённая новая личность.

### Настройки

`settings.json` в том же каталоге, что у Tauri-клиента. Поле `ptt` оболочка
читает, но не трогает — вернувшийся на Tauri-сборку найдёт свою комбинацию на
месте. Автозапуск — файл `~/.config/autostart/relay.desktop` с тем же именем и
тем же аргументом `--hidden`, что пишет tauri-plugin-autostart: одна запись на
две оболочки, а не две спорящие.

### Диагностика

Всё интересное пишется в `~/relay-update.log` — тот же файл и тот же формат,
что у Tauri-клиента: окружение (сессия X11/Wayland, версии Electron и
Chromium), след навигаций, решения по разрешениям, обновления. Первый вопрос
при «не работает» — этот файл.

## Сборка

Всё в Docker, локальный Node не нужен:

```bash
docker run --rm -v "$PWD":/mono -w /mono/clients/desktop-linux node:20-bookworm-slim \
  sh -c 'npm install --no-audit --no-fund && npx electron-builder --linux AppImage'
# → clients/desktop-linux/dist/relay_<версия>_linux_x86_64.AppImage
```

Раздаётся **AppImage** — один файл, работает везде и умеет обновляться сам.
deb/rpm/AUR у этой оболочки нет: пакетный менеджер обновляет сам, а смешивать
две дороги обновления в одном продукте — способ однажды затереть чужие файлы.

## Стенд: живой звонок в Docker

Оболочка проверяется не «собралась», а «звонит»:

```bash
./clients/desktop-linux/testbench/run.sh
```

Скрипт поднимает прод-стек с e2e-оверлеем, собирает образ стенда (Playwright +
Electron той же версии) и гоняет `e2e/tests/linux-shell.spec.ts` — тот запускает
**настоящую оболочку**, ведёт её через экран выбора сервера, заводит человека и
звонит обычному Chromium. Проверяются разом: соединение (миллисекунды из
`getStats`), мост на удалённом origin, файл ключа с правами `0600` и ответ
оболочки с настройками.

## Обновления и переезд с Tauri-сборки

Обновляется только AppImage, `electron-updater` читает `latest-linux.yml` из
`releases/latest/download/`. Провайдер — `generic`, а не `github`, намеренно:
теги десктопа выглядят как `desktop-v1.0.0`, и github-провайдер спотыкается о
такой тег, разбирая его как версию.

Установленные Linux-клиенты на Tauri переезжают сюда одним разом: их апдейтер
заменяет файл AppImage целиком, а `latest.json` для платформы `linux-x86_64`
указывает на эту сборку (подписанную тем же ключом обновлений). После этого
клиент обновляет себя уже сам.
